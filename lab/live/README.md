# 120 星持续实时运行

常驻的软件在环运行模式：按当前时间计算 120 颗卫星的位置和接触关系，更新实际 FRR 网络，并保持同一个 5G UE / PDU 会话持续发包。默认没有结束时间，不读取或循环播放归档的 31 帧。

## 启动、查看、停止

在工程根目录执行：

```bash
make live-start
python3 frontend/server.py
```

打开 **http://127.0.0.1:8090/?mode=live**。前端也提供“启动 120 星”和“停止运行”。启动会检查并构建当前 Go / Rust 程序，然后依次启动 5G、3 节点 Kubernetes、144 个 FRR 路由器（120 星 + 24 网关）、监控和 120 个星上程序。冷启动需要数分钟，页面会显示实际阶段。

```bash
make live-status
make live-stop
```

关闭网页或停止前端服务不会停止星座。停止星座会先停止业务探测、撤销本轮路由，再清理本轮星上、FRR、云控、监控和 5G 资源；Mongo 测试卷沿用原有 5G 清理规则。其他独立实验的容器不属于本轮资源。

也可使用 `python3 lab/live/service.py start|status|stop`。服务有进程锁，重复点击启动不会部署第二套共享同一 5G 端点的系统。

### 启动进展与 Kubernetes 诊断

启动页面自动显示 13 个主阶段，以及实际执行的子步骤：构建镜像、创建集群、逐镜像逐节点导入、安装 Cilium / Hubble、等待节点与探测 Pod、部署控制器和选主。FRR 阶段另记录容器创建、链路连线和 OSPF 邻居检查。

- **当前操作与耗时**：显示正在做什么、目标节点／镜像、操作的超时上限。完成数是实际通过的阶段数量，不是预计剩余时间。
- **最近诊断采集**：守护进程每 5 秒读取本轮 Docker / Kubernetes 状态；页面每 3 秒刷新。监测在响应不等于部署步骤已完成。
- **最近步骤进展**：只有实际进入、完成、失败或收到 5G 检查点时更新。长时间等待不会通过刷新伪造进度。
- **节点与 Pod**：显示节点 Ready、Pod 阶段、就绪容器数、重启次数、等待原因及最近 Warning 事件。历史警告可能已恢复，应结合当前状态判断。控制器采用单主就绪机制，3 个副本中预期只有主实例 Ready。
- **常驻租约**：120 星常驻模式使用 30 秒 Lease、5 秒重试／Kubernetes 请求时限，以容纳本机并行更新时的调度延迟。独立 HA 故障门禁仍使用 6 秒／1 秒配置；常驻模式不会据此宣称完成同样的快速接管验收。
- **批量切换收敛**：常驻网络使用 OSPF 2 秒初始延迟、5–15 秒重算保持时间及 IS-IS 5 秒 SPF 间隔，合并大批接触变化；三个 Kubernetes 节点的 CPU 相对权重为单个 FRR 容器的 8 倍。FRR 状态查询按协议隔离，并在容器内设置 20 秒超时，避免失去响应的协议阻塞其他业务观测。这些设置不保证 10 秒内完成全部切换。
- **诊断过期／断开**：页面明确提示，保留上次观测；API 尚未创建时显示等待，实际命令失败时保留错误，未执行步骤不会被标为通过。
- **启动完成后**：在“实时控制器 → 查看本轮启动诊断”中查阅记录，或导出诊断 JSON。运行期间不持续轮询 Kubernetes 启动诊断。

本轮记录保存在 `reports/live/progress.json` 和 `reports/live/diagnostics.json`，均按启动会话隔离，重新启动不会显示上一轮的检查点。诊断读取使用本轮集群专属 kubeconfig。

默认实时输入为（原 `leo-120.config.json` 的四网关独立验收配置保持可用）：

- `scenarios/constellations/leo-120-global.config.json`
- `scenarios/constellations/physical-defaults.json`
- `scenarios/constellations/live-workloads.json`

`SF_LIVE_CONSTELLATION=/absolute/path/config.json make live-start` 可以选择其他星座规模；每个网关必须在物理配置中有坐标。

`duration_seconds` 是旧有限时长实验的参数，**不限制常驻模式**。默认步长 10 秒；启动前可设 `SF_LIVE_STEP=20 make live-start`。`SF_LIVE_DURATION=600 make live-start` 仅用于有界集成验证，表示准备完成后运行 600 秒再清理；默认 `0` 表示持续到主动停止。

## 24 个全球网关与 384 条并行业务

新启动的实例保留 120 颗卫星，使用 24 个分布在六大洲的工程设计站点，默认加载 8 类业务、每类 48 条。`pairing: balanced_mesh` 按不同网关偏移轮转：每个网关在每类业务中各发起 2 条、接收 2 条，全部业务覆盖 276 对不同网关。每条业务使用独立地址和真实 TCP/UDP socket；既有 5G N3 业务继续运行，不把这些测试流算作新增 UE 或 PDU 会话。

384 是默认编排数量，不是已验证的稳定容量。容量测试固定 120 星、24 网关和单流发送速率，独立冷启动后检查动态切换、逐流回包、有效速率和连续稳定窗口；`python3 -m lab.live.capacity --help` 提供监测入口，本机逐档证据和判定标准见 [容量测试记录](../../reports/capacity/README.md)。初始全部连通或不同时间累计全部连通，均不代表动态稳定通过。

| 业务 | 控制方式 | 实际承载 | 单流应用速率上限 |
|---|---|---|---|
| 遥测 | 分布式 | OSPFv2 通告 IPv4 端点与选路 | 64 kbit/s UDP |
| IPv6 运维 | 分布式 | OSPFv3 通告 IPv6 端点与选路 | 32 kbit/s UDP |
| 指令 | 集中 | 控制器逐跳 IPv4 静态路由 | 64 kbit/s UDP |
| 批量传输 | 混合 | 控制器选入口下一跳，IGP/LDP 决定后续标签转发 | 512 kbit/s TCP |
| 视频 | 混合 | 控制器路径编译成 SR-MPLS Prefix SID 栈；IS-IS 分发 SID | 1 Mbit/s UDP |
| 动态路径指令 | 混合 | BGP-LS 校验拓扑 → PCEP PCReq/PCRep → BSID / SR-MPLS | 64 kbit/s UDP |
| 交互 | 混合 | IPv6 段列表与 SRv6 解封装；OSPFv3 维护 Locator 可达性 | 128 kbit/s UDP |
| 企业互联 | 混合 | 入口转入 EVPN/VXLAN 网关互联；IGP 决定隧道底层路径 | 256 kbit/s TCP |

配置的单向应用负载上限合计 **101.76 Mbit/s**；默认 `initial_rate_fraction:0.25`，启动目标为 **25.44 Mbit/s**，回显会再产生相当的反向应用流量，实际链路流量还包括封装与协议开销。这是协议和路径验证负载，不是卫星吞吐量上限测试。384 条流中 96 条由分布式协议选路；其余 288 条产生 576 个双向控制器意图，加上 48 个基础网关意图及 2 个 N3 意图，共 626 个。各协议承担不同职责，不把所有封装套在同一个包上。LDP 和 EVPN 的底层路径并不等于控制器完整显式路径。

启动前可在 JSON 中设置单类 `rate_bps`、`payload_bytes`、`dscp`、`priority`、`max_rtt_ms`、`copies_per_profile` （1–64）、`pairing`（`balanced_mesh` 或兼容的 `ring`）、全局 `rate_scale` 和启动发送比例 `initial_rate_fraction`（0.1–1）。`SF_LIVE_WORKLOADS=/absolute/path/config.json make live-start` 可选择另一配置；设 `enabled:false` 可关闭新增流量。已运行实例不会因源文件被修改就自动加载新编排。

“业务”页面首先显示全球城市网关矩阵；点击网关对可查看对应业务，支持按网关、协议筛选，每页最多 48 条。地球视图使用真实模型站点坐标显示城市，节点总数来自本轮实例。

“业务”页面可以在线选择配置速率的 10%、25%、50%、75%、100%，下一采样周期生效。控制器继续按配置上限预留容量；增加上限需要重新配置后启动。启动发送比例不改变控制器容量预留。页面区分上限、工作进程实际应用的目标速率与实测有效速率。有效速率只计算带本轮标识的回包应用字节；RTT、抖动、超时比例均来自真实收发。TCP 未完成比例是应用超时，不等同于底层网络丢包率。DSCP、优先级和时延目标不代表已经实现带宽或时延保证。

协议页分别显示路由配置状态、同一业务报文在卫星节点上的封装证据，以及故障验收状态。抓包校验运行标识、端点和封装，旧计划的集中控制抓包不能证明新计划。封装未就绪的业务保留独立丢弃路由，避免退回普通 IP 后被误判通过。各星观测包数可能重复，不作为唯一送达数量。历史 5G 同会话故障矩阵与新增 TCP/UDP 回归分别记录。

PCEP 请求发出后会在本轮更新内复查 PCRep 和实际 BSID，标签栈、下一跳与接口均匹配后才恢复入口转发，避免等待下一次整轮轨道更新。复查轮询预算为 8 秒，单次 FRR 查询仍受操作超时约束；未就绪业务继续保持独立丢弃路由。

大规模回归按每个阶段的有界观测窗口逐条收集双向封装证据，并记录各条证据时间和同时验证数量；阶段切换或路径变化会使旧证据失效。报告保留最新抓包状态，不把跨次采样的覆盖率当作同一瞬间全部验证。

运行证据在本轮目录的 `workloads/`：`catalog.json`、`metrics-gw-*.json`、`snapshot.json`、`capture-latest.json`、`capture-latest.pcap` 和轮转 PCEP 日志。当前指标、操作与抓包覆盖更新，保留有界内存和文件大小。

## 数据如何流动

```text
当前 UTC + 单调时钟
  → OrbitClock：实时 SGP4 / TLE / OEM 位置与接触计算
  → LiveFabric：稳定地址、新链路创建、过期接口回收
  → 实际接口与 tc 队列参数更新
  → 拓扑批量事件 → 路由预览 → 按需提交 → 实际设备验证
  → 5G 业务、星上状态、控制器返回值
  → 原子更新实时快照 → 前端每 3 秒读取
```

启动期间固定初始快照，等待部署和协议收敛。业务就绪后先发布真实的启动保留快照，保留原始模型和应用时间，再进入轨道更新。进入运行阶段后按当前时间继续计算；首轮可能因轨道跨越启动耗时而发生多条链路切换，页面保留实际丢包及降级结果。

设计 Walker 星座以本次启动时刻作为轨道历元；TLE / OEM 保持输入定义，OEM 覆盖不足会报错，不会回到旧数据。显示的卫星位置属于物理模型，未连接真实在轨卫星遥测。

### 时间与性能

实时星座只把 BGP-LS 拓扑发送到实际采集网关，EVPN 仍保留全部网关互联；EVPN 就绪检查每网关读取一次路由表，缺失地址保存在 `evpn-convergence.json`。

控制器的网关可达性探测最多并行 8 路，相同源网关与目标地址合并探测；各业务的回包指标与封装证据仍独立采集。大规模路由提交保留逐批回读校验，客户端等待上限为 240 秒。实时队列更新采用全网关闭／整形／开启三阶段，最多并发 4 个节点，单次命令上限 60 秒；暂时失败会重试同一帧一次，完成后才发布成功状态。

这是尽力跟随真实时间的软件在环系统。目标步长为 10 秒；若某次网络下发或路由提交超时，下一次计算当时的新状态，记录错过的采样时隙。捕获与终端选择状态会按模型步长补算中间状态，实际网络只应用最新一帧，避免把处理延迟误认为全部链路刚开始捕获。不会压缩旧帧来伪装跟上时钟。

界面分别显示模型时间、实际链路应用时间、样本年龄和应用耗时。轨道连续运行不等于每个时刻都存在符合容量、备份要求的业务路径；不能规划时显示降级，保留最后提交记录并继续尝试后续状态。

### 动态链路

链路地址和接口名称由两个节点的固定序号确定。新链路先以 DOWN 状态创建、配置协议与队列，然后按模型启用。消失链路先实际关闭并发布，再在 120 秒后删除空闲接口。再次相遇时复用相同地址。

控制器保留已关闭链路的拓扑记录，其数量受固定节点组合数限制。下一跳使用 `live-pair-v1` 节点编号规则计算，取代每节点完整邻居地址表；120 星 / 24 网关及 384 条业务的控制器配置经过 Kubernetes 1 MiB 限制检查。当前 live 地址池支持最多 255 个总节点。

### 运动中的星上自治

实时模式为 Rust 程序配置 `fallback_targets`：目的前缀和出口网关 Loopback。心跳超时后，各星查询本机内核中的 IGP 路由，安装实际下一跳；自治期间持续重查，发生接触切换后更新备用路由，出口不可达时撤回旧路由。

这项查询由星上程序完成，地面不需要继续下发备用下一跳。地面控制路径恢复并有可用提交后，恢复心跳并撤回当前备用路由。IGP 收敛及链路覆盖缺口仍可能造成业务丢包。

旧 `fallback_routes` 静态配置保持兼容。原有固定时长物理验收、六种承载故障矩阵和 A/B 更新入口继续保留。

### 记录与边界

- `reports/live/status.json`：运行阶段、进程、时间、序号、错误。
- `reports/live/snapshot.json`：最近 31 次轨道状态、实际计划、120 星状态和业务计数。
- `reports/live/service.log*`：启动与停止日志，轮转保存。
- `lab/unified/artifacts/<run_id>/`：本轮启动配置、滚动事件与当前网络操作记录。
- 内存只保存有限窗口：31 次轨道状态、180 次耗时记录、1800 个 RTT 样本、120 个事件。
- 探测和事件日志轮转；当前网络操作文件覆盖更新；控制器/执行代理日志限制大小；实时 NOC 使用 24 小时保留窗口，Prometheus 另设 1 GB 上限。
- 实时业务计数取自实际 ICMP 回复和未应答序号；未决或迟到报文会影响即时丢包值。不是全流量计费计数器。
- 常驻模式保留 native N3 用户面，同时编排上述 384 条多协议 TCP/UDP 业务。完整故障矩阵属于独立验收流程，不会因“实时运行中”而自动标为通过。
- 部署中断、运行错误和过旧数据会明确显示。主机重启后需要重新启动本轮系统；目前不提供整套业务跨主机重启续接。

```bash
python3 -m unittest frontend.test_server -v

```

```bash
python frontend/browser_check.py       # 历史页面回归
```

### 扩容回归

`python3 lab/live/validate_workloads.py --gateways 24 --copies 48 --faults` 在独立的 24 网关、6 颗卫星拓扑上验证 384 条业务的初始转发、断链和恢复；默认无参数仍为 2 网关 / 32 条业务。回归与完整实时星座使用同一套稳定接口地址规则。隔离回归结果不替代 120 星运行的当前业务证据。
